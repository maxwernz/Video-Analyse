# Handoff: Prototype A -- redesigned Qt Widgets interface

You are building **one of two competing throwaway prototypes**. Prototype B is a
full-window QML / Qt Quick presentation layer, built in parallel by another agent
from `HANDOFF-prototype-b-qml.md`. You are not building the production migration.

**You are not the fallback option.** The shipped Widgets interface looks cheap,
but that is a design failure, not proof that Widgets cannot reach the bar. Your
job is to find out whether a carefully redesigned Widgets interface reaches the
reference quality -- and, just as importantly, what it costs in custom painting to
get there.

## Read first

1. `docs/design/desktop-ux.md` -- the direction, the fairness rules, the decision
   criteria and the kill conditions. Authoritative.
2. `docs/design/visual-tokens.md` -- **frozen**. Colours, type, metrics, icons and
   the canonical fixture. Consume exactly; do not tune, do not edit this file.
3. `docs/design/references/` -- Catapult (primary), In-Play (secondary),
   TactiCode. Visual character only, never features.
4. `docs/design/current-ui/` -- what is being replaced, with the worst areas
   marked. Read `*-marked.png`; every marked failure is something you must fix.
5. `docs/adr/0007-branded-dark-visual-system.md` and
   `docs/adr/0006-one-compact-timeline-as-the-sole-seek-surface.md`.

## Build in

`prototype/presentation_a_widgets/` and nowhere else.

## What to build

Two screens, at a designed minimum of 1440x900:

1. **Normal workspace** -- 44px working toolbar (no product wordmark), left
   sidebar with Clips/Videos as a segmented control, Clip list grouped by
   Category with 32px rows, near-black video stage, the 60px timeline, the 56px
   transport.
2. **Clip-editing state** -- large paused frame left, 360px sectioned form right,
   monospace scrub-linked boundary fields with a live duration readout, accent
   primary and quiet secondary actions.

Also render the **empty state** if time allows: the designed drop target, not a
black rectangle.

Specific failures from the marked captures that you must not reproduce: the
product wordmark strip, the tree column header, coloured-text-only Category cues,
proportional digits in timecode columns, the unstyled scrollbar, mismatched
raster icons, a stock `QComboBox` for playback speed, and clipped duration
fields in the editor.

## Technique -- the point of the exercise

"Mostly native Widgets" means native structure and native behaviour, not a stock
appearance. Expect to need:

- A single stylesheet driven by the frozen tokens -- one source, no per-widget
  ad-hoc styling.
- A `QStyledItemDelegate` for the Clip list, so rows carry the Category bar,
  13px title and right-aligned monospace timecode without a column header.
- A custom-painted timeline widget: 16px ruler with adaptive labelled minute
  marks, 44px track, Clip ranges as filled bars at 40% alpha with a 1px
  full-colour top edge, a 2px accent playhead with a grabbable handle, hover
  cursor line and timecode tooltip, and the full ADR 0006 interaction grammar
  (drag anywhere scrubs, click a range selects without seeking, double-click
  seeks to the Clip start).
- SVG icons rendered through `QIcon`/`QSvgRenderer` so they recolour by state and
  stay crisp on HiDPI.
- A replacement for the speed `QComboBox` -- a menu button or segmented control.

Keep native behaviour: native menu bar, native window controls, native file
dialogs, platform shortcuts.

Retain `analysis/`, `application_workflow.py` and `playback/` as-is; the
prototype is a presentation layer over existing logic, exactly as B is.

**Track the cost as you go.** Count the lines of custom `paintEvent` and delegate
code the visual bar requires. A's named kill condition is that reaching the bar
turns the timeline and transport into unmaintainable custom painting, so this
number is evidence, not bookkeeping.

## Do not

- Modify anything outside `prototype/presentation_a_widgets/`, except appending
  your findings to your own README.
- Touch `prototype/presentation_b_qml/` or read it before you have finished your
  own build. Parallel isolation is what makes the comparison fair.
- Edit `docs/design/visual-tokens.md`. If a value is genuinely wrong, note it in
  your findings and use it anyway.
- Adopt any excluded reference feature: annotation tools, tagging button grids,
  stacked lane timelines, event registry tables, sharing or multi-user chrome.
- Reuse `visual_system.py` as a starting point. It encodes the superseded
  direction; start from the frozen tokens instead.

## Deliverables

1. A runnable prototype: `README.md` with the exact run command.
2. Screenshots at 1440x900 in `prototype/presentation_a_widgets/screenshots/`,
   one per screen, same fixture as the spec.
3. `FINDINGS.md` reporting **against the five decision criteria** in
   `desktop-ux.md`: visual result, timeline rendering and interaction quality,
   playback and scrub performance, packaging on macOS **and** Windows, and how
   much Python the presentation layer needs plus how testable it stays.
4. An explicit verdict on A's **kill condition**: how much custom painting the
   visual bar actually required, and whether that volume is maintainable.
5. An honest list of what you could not make work. A prototype that hides its
   failures is worthless for this decision.

Report packaging as a real observation -- attempt a build with the existing
`scripts/build_macos.sh` path and say what breaks -- not as an estimate.
